Complete the [analysis DSL example](/docs/latest/analysis/dsl/#complete-example-and-shared-inputs) first. Save the following in a new script in the same project. This uses the six-order dataset and UTC reporting time. The start is included and the end is excluded. Run each section in order.

The example Session has `session.timezone == "UTC"` and
`session.timezone_origin == "explicit"`. A new Session also accepts an explicit
offset such as `timezone="+08:00"`. Omitting the timezone strictly resolves the
system IANA zone once; ambiguous `TZ` or localtime state requires an explicit
value. Recovery keeps the saved timezone and origin without checking the host.

Source time comparisons use the same boundary rules as `session.time_scope`.
Bare ISO dates, Python `date` values and offset-free ISO timestamps use the
Session's report timezone; aware datetimes and ISO timestamps with an offset keep
their instant. This covers `observe(where=...)`, `members(where=...)`,
`Metric.where(...)` and a source reducer's `where=`. Invalid ISO, naive Python
datetimes and ambiguous/nonexistent local clocks reject before source reads.
Using the example's order time field, capture explicit half-open field bounds:

```python
from analysis import session

created_at = session.catalog.get("time_dimension:sales.orders.order_date")
start = session.instant("2026-08-01", timezone="Asia/Shanghai")
end = session.instant("2026-09-01", timezone="Asia/Shanghai")
by_boundaries = (created_at >= start) & (created_at < end)
```

An output calendar's timezone does not change the implicit comparison timezone.
Use `session.instant(..., timezone=...)` to choose an explicit boundary timezone.
A field predicate does not provide report endpoints or calendar completion, and
stays in force during the full window, including history before the report range.
Use `where=scope` for an unbucketed report range or `by=(scope.by(day),)` for
calendar buckets instead. DATE rows compare their declared business-day-start instant; `==` means one exact
instant. Ordinary string fields and fixed Frame Column comparisons retain their
own types, and saved results are not reinterpreted.

Report TimeScopes and CalendarAxes must use the receiving Session timezone, including shifted axes and domains supplied through a Population. Create a separate Session for another report timezone; a domain created by a different Session is accepted only when its timezone matches.

Ordinary time grouping uses actual contributions without filling buckets. A window
supports an endpoint through actual contributions in that window: history can produce
a row even when the current bucket has no new facts. A completely empty window does
not create a row; real zero and all-NULL history still support it. Use explicit
`by=Population` for every date and empty-window values. The calendar directory keeps
all selected positions, so `read_periods()` can include dates absent from the main
table. Shift, offset, ordinal and trailing_periods never renumber visible rows.

## Observe days and months

```python
from analysis import mv, session, revenue, amount, region, august
```

{/* example: calendar-query */}

```python
day = mv.grain("day")
daily = session.observe({"revenue": revenue}, by=(august.by(day),)).compute()
sum_of_days = daily.reduce({"sum_of_days": daily["revenue"].sum()}).compute()
sum_of_days.show()
monthly_source = session.observe({"revenue": revenue}, by=(august.by(mv.grain("month")),)).compute()
monthly_source.show()
```

Natural calendars use `mv.grain(...)` and explicit `scope.by(grain)`. Fiscal periods, holidays and working days use ordinary business fields; the harness chooses authority, ranges and pairing. See [dates and time](/docs/latest/modeling/dates/).

Report grain never replaces the Metric's contribution clock. A DATE-clock Metric
cannot become hourly by changing `grain` or passing a TimeDimension directly in
`by`. An existing `hour_prefix` field can supply an explicitly chosen partition-hour
clock; changing clocks may change membership and totals. See the
[partition-hour example and classification alternative](/docs/latest/modeling/dates/#separate-hour-column-mshour_prefix).

{/* example: metric-window-query */}

```python
from datetime import timedelta

rolling = session.observe(
    {"revenue": revenue.window(mv.trailing_duration(duration=timedelta(days=7)))},
    by=(august.by(day),),
).compute()
month_to_date = session.observe(
    {"revenue": revenue.window(mv.to_date(grain=mv.grain("month")))},
    by=(august.by(day),),
).compute()
rolling.show()
month_to_date.show()
```

{/* example: period-comparison-query */}

```python
current_scope = session.time_scope(start="2026-08-01", end="2026-08-04")
prior_scope = session.time_scope(start="2026-07-01", end="2026-07-04")
current_daily = session.observe(
    {"revenue": revenue}, by=(current_scope.by(mv.grain("day")),)
).compute()
prior_daily = session.observe({"revenue": revenue}, by=(prior_scope.by(mv.grain("day")),)).compute()
comparison = current_daily.compare(
    {"reference": mv.baseline(prior_daily, match=mv.ordinal())}
).compute()
comparison.show()
```

{/* example: shifted-period-comparison-query */}

```python
months = session.time_scope(start="2026-08-01", end="2026-08-20").by(mv.grain("month"))
current_progress = session.observe({"revenue": revenue}, by=(months,))
previous_progress = session.observe(
    {"revenue": revenue},
    by=(months.shift(mv.offset(periods=-1)),),
)
progress = current_progress.compare({"mom": mv.baseline(previous_progress)}).compute()
progress.show()
```

## Interpret windows and correspondence

August's total is 800. At the end of August 5, trailing seven-day revenue is
100; month-to-date through August 15 is 200. A trailing window can reach before
the displayed range, so include the required lookback history in the source data.

`trailing_duration` measures elapsed time: seven days is 168 hours. Civil
periods follow calendar boundaries and can span different amounts of elapsed
time around daylight-saving changes. Each window ends at the bucket's actual
right boundary; `to_date` resets at the start of the selected period.

Ordinal matching pairs positions in compatible, complete periods. The daily
scopes `[August 1, August 4)` and `[July 1, July 4)` each contain three days and
pair by position. Shifting the monthly prefix `[August 1, August 20)` back one
month compares it with `[July 1, July 20)`, excluding July 20 midnight and
later. The example compares 200 with 300, a change of -100. A missing target
date remains absent instead of moving to a nearby date.

`mv.offset(periods=n)` counts steps of the consuming axis's grain, not visible
rows or fixed-day durations: on daily data, `-7` is seven days; on weekly data,
`-1` is one week; and on monthly data, `-1` is one month. Built-in calendar
offsets require grain `count=1`; subday offsets are unsupported.

Summing result rows computes statistics over those rows. Observe the original
Metric at monthly grain for a monthly ratio or distinct count. Natural calendars
use `mv.grain(...)` and explicit `scope.by(grain)`. Fiscal periods, holidays and
working days use ordinary business fields; the harness chooses authority, ranges
and pairing. See [business calendars and holidays](/docs/latest/modeling/dates/#business-calendars-and-holidays).

Source parsing and report timezones are separate: set a parser timezone for
naive source values; aware timestamps already identify an instant, and date-only
values use their declared source timezone to identify the business-day start.
Projection, filtering and buckets share the
actual backend's native gap/fold interpretation. Original local time data uses
pandas native operations. Different executors can differ at unusual transitions;
source-produced keys remain unchanged during local arithmetic and alignment.

`ms.hour_prefix(date_field)` uses the source timezone context of its date prefix.
Changing the report timezone does not reinterpret that source timestamp.

## Time means and sample coverage

`sample_interval=(1, "hour")` declares source cadence without rounding timestamps
into hourly buckets. All TimeField sample reducers use represented timestamps,
allow missing clocks and never implicitly fill them with zero or NULL.
NULL, empty-input and weighted valid-pair policies remain reducer-owned.
An explicit `Population` still selects its declared sample coordinates.

In the six-order example, first average order amounts per date, then average
the represented dates within each region. Only dates with orders participate,
and each date has equal weight; when order counts differ by date, this can differ
from an order-weighted mean. August gives 100 for east and 600 for west; adding
zero to each daily mean leaves those results unchanged.

```python
order_date_entry = session.catalog.get("time_dimension:sales.orders.order_date")
assert order_date_entry.kind == "time_dimension"
order_date = order_date_entry
samples = amount.mean(time=order_date).per(order_date)
sample_mean = session.observe({"average": samples.mean()}, where=august, by=(region,)).compute()
# Arithmetic does not add a clock-coverage requirement.
adjusted = session.observe({"average": samples.mean() + 0}, where=august, by=(region,)).compute()
sample_mean.show()
adjusted.show()
```

Natural calendar samples consume actual represented keys; output completion does not add samples. Windows retain their endpoint requirements. The harness supplies explicit ranges for business calendars.


Qualified source-backed samples finish at the source: each timestamp's child
Metric completes before the outer mean, quantile or other reducer. Compatible
summaries share the inner calculation. For example, `amount.sum(time=order_date).per(order_date).quantile(0.95)` computes a quantile of completed daily sums.
Explicit Population sample domains retain their completion rules; calendar samples use actual keys.
Native arithmetic and Decimal rounding follow the backend; unsupported type or
algorithm combinations retain their existing local route. A native failure does
not trigger local recomputation. Completed Frames continue to use captured data.

## Fold Metrics over calendar cells

Use `Metric.per(grain)` to fold completed buckets by each source component's
declared contribution time. Use `Metric.per(created_at, grain=mv.grain("day"))`
to fix the sample field while the original Metric keeps its contribution time. Grain-only
sampling needs at least one clocked branch; explicit fields and Populations supply their own sample domains. Both builtin forms use the Session report timezone and need no finite
observation period. If you previously chose the sample timezone through an
observation axis, set the Session timezone explicitly. An all-NULL day with
contributions is still a sample. A missing day adds no sample.

{/* example: calendar-sample-fold */}

```python
week = mv.grain("week")
daily_average = revenue.per(mv.grain("day")).mean()
folded = session.observe({"daily_average": daily_average}, by=(august.by(week), region)).compute()
folded.show()
```

For a completed `daily_p95`, use `daily_p95.per(mv.grain("day")).median()`
under the same weekly axis. Empty ratios and quantiles remain NA and follow the
sample reducer's existing NULL policy. TimeField and Grain samples use actual
keys; final output completion does not affect their mean or count. Builtin nesting
is static: day in week/month is valid; week in month rejects. Divisible subday
widths, month in quarter/year and quarter in year are supported at every layer.
The Grain in `per` selects internal
sample buckets; the CalendarAxis in `observe(by=...)` selects report buckets. Help: `semantic.metric.per`.

Natural calendar samples consume actual represented keys; output completion does not add samples. Windows retain their endpoint requirements. The harness supplies explicit ranges for business calendars.

{/* example: calendar-sample-window */}

```python
from datetime import timedelta

rule = mv.trailing_duration(duration=timedelta(days=7))
day = mv.grain("day")
window_daily_mean = revenue.per(day).mean().window(rule)
mean_daily_window = revenue.window(rule).per(day).mean()
window_comparison = session.observe(
    {"window_daily_mean": window_daily_mean, "mean_daily_window": mean_daily_window},
    by=(august.by(mv.grain("week")),),
).compute()
```

The first expression averages actual daily revenues inside each report window.
The second discovers actual dates in each report bucket, evaluates a window at
each date's selected end, then averages those window values. Missing dates do not
participate; history does not create new sample dates. `trailing_periods` uses the
report grain in the first expression and the sample grain in the second.

`amount.sum(time=paid_at).per(created_at, grain=day).mean()` selects revenue by
payment time and averages creation-day groups. For creation-attributed revenue,
use `amount.sum(time=created_at).per(day).mean()` instead. An inner window on
an explicit creation-day sample retains that cohort and uses the creation day's
end; payment time still determines which cohort contributions enter the window.
Fixed source predicates remain in force. Multiple windows on one dependency path
remain unsupported.

Window endpoint facts are captured in each contribution's `window_endpoint` under
`frame.schema.value_time_semantics`. They distinguish report, contribution-clock
sample, and explicit-field sample endpoints and survive persistence.


## Historical classification for each fact

This fragment requires a declared versioned `sales.profiles`, fact Entity
`sales.facts`, and complete-key relationship `sales.profile`. Control time and
Metric time are independent choices; this example explicitly uses the same field.

```python title="Requires a versioned profiles model"
control = session.catalog.get("time_dimension:sales.facts.event_time")
# The control may also be the fact Entity's snapshot partition TimeDimension.
label = session.catalog.get("dimension:sales.profiles.label")
route = session.catalog.get("relationship:sales.profile")
amount = session.catalog.get("measure:sales.facts.amount")
historical = label.via((route,)).at(control)
scope = session.time_scope(start="2026-08-25", end="2026-09-08")
day = mv.grain("day")
daily = session.observe(
    {"value": amount.sum(time=control)}, by=(scope.by(day), historical)
).compute()
restated = session.observe(
    {"value": amount.sum(time=control)},
    by=(scope.by(day), label.via((route,)).at(session.instant("2026-09-03T00:00:00+00:00"))),
).compute()
```

Row time selects an attribute for each original fact; a fixed anchor restates the entire window under one definition. For contributions 7/11 with labels A/B before/after a change, row time gives A=7, B=11; a fixed new anchor gives B=18. The fact Entity may be unversioned or snapshot-versioned. Its native snapshot partition TimeDimension can control matching, so the same stable key on different days retains each day's contribution without a daily query loop. Qualified same-source single-root observe by/where is supported on DuckDB/Trino. NULL control or missing versions preserve NULL labels without fallback. DATE selects target business dates; timestamp validity requires timestamp control. Native absolute timestamps and UTC/fixed-offset local clocks are admitted. Validity fact roots, IANA local clocks, read/classify, multiple roots and window/per compositions require fixed anchors. Bucket-end reclassification is a separate question.


## Inspect captured source time interpretations

After computing `daily`, inspect `daily.schema.source_times` or call
`daily.show()`. Each immutable record identifies the consumed source field,
physical type and consumption timezone. `instant` needs no source declaration;
`wall_clock` and `civil_date` retain the effective source timezone and its
`field` or `datasource` origin. Hour-prefix clocks also record `inherited_from`.
Pending display never opens a source to obtain these facts.

The records describe consumed inputs. Fixed selection, renaming, filtering,
fixing, arithmetic and reduction retain them; combinations merge complete
records, including different interpretations of the same field path. A business
date whose source and consumption zones differ is assigned by its day start;
business-day totals cannot reconstruct event-day totals. Persisted Frames keep
these facts, captured absolute ranges and bucket keys unchanged during cold
recovery, even when the host timezone changes or sources and models are offline.

```python
facts = daily.schema.source_times
for fact in facts:
    print(fact.axis, fact.kind, fact.consumption_timezone)
```

## Mixed windows and shifted output domains

Ordinary and windowed Metrics discover categories jointly, including categories
represented only in lookback history. Selected endpoints stay fixed. Every final
time key needs an endpoint on each window branch; an extra ordinary key without
one causes an error. A defined endpoint without facts still uses the reducer's
empty-result rule. This also applies to mixed formulas.

Shifted observations retain their exact sparse selection and direct relation.
An extra native key without a shift mapping, conflicting native bucket meanings,
or incomplete mapping coverage rejects before completion or publication. A legal
missing target period remains absent, rather than becoming a zero-valued bucket.
Automatic compare requires the current directory to match the baseline's saved
immediate origin; independently valid results can still need an explicit supported
correspondence. Completed and reopened comparisons use saved data without rereading sources.


Windows filter clocked leaves only; independent leaves retain their value at each valid endpoint. Fully independent windows need established output keys or a range total, with valid endpoints and rules; they do not create time coordinates. Explicit output completion does not create internal samples for a mean.
