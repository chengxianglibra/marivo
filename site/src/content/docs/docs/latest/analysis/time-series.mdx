```python
days = august.by(mv.grain("day"))

sum_of_days = daily.reduce({"sum_of_days": daily["revenue"].sum()}).compute()
sum_of_days.show()

    {"revenue": revenue}, by=(august.by(mv.grain("month")),)
```

{/* example: metric-window-query */}

```python
from datetime import timedelta

rolling = session.observe(
    {"revenue": revenue.window(mv.trailing_duration(duration=timedelta(days=7)))},
    by=(days,),
).compute()
month_to_date = session.observe(
    {"revenue": revenue.window(mv.to_date(grain=mv.grain("month")))}, by=(days,)
).compute()
rolling.show()
month_to_date.show()
```

{/* example: period-comparison-query */}

```python
current_days = session.time_scope(start="2026-08-01", end="2026-08-04").by(mv.grain("day"))
prior_days = session.time_scope(start="2026-07-01", end="2026-07-04").by(mv.grain("day"))

comparison = current_daily.compare(
    {"reference": mv.baseline(prior_daily, match=mv.ordinal())}
).compute()

```

{/* example: shifted-period-comparison-query */}

```python
months = session.time_scope(start="2026-08-01", end="2026-08-20").by(mv.grain("month"))

previous_progress = session.observe(

progress.show()
```

## Interpret windows and correspondence

August's total is 800. The seven-day trailing revenue at the end of August 5 is 100; month-to-date at August 15 is 200. Lookback can extend before the displayed start, so provide that history for real data.

`trailing_duration` measures elapsed time. Civil periods follow calendar boundaries and can differ across daylight-saving transitions. The window's endpoint is the bucket's actual right boundary. `to_date` resets at the selected period boundary.

Ordinal matching pairs original positions in compatible complete periods. A month shift of the August 1–20 prefix compares with July 1–20, without including July 20 midnight or later. The sample therefore compares 200 with 300, a change of -100. A missing target date is not silently clamped to another date.

`mv.offset(periods=n)` counts steps of the consuming axis's grain, including its grain step. On daily data `-7` means seven days; on weekly data `-1` means one week and `-7` means seven weeks; on monthly data `-1` means one month. A negative offset seeks an earlier baseline. It does not count displayed rows or fixed days. Builtin calendar grains currently require `count=1`; subday offset is unsupported.

Summing result rows is a statistic on those rows. For a monthly ratio or distinct count, request the original metric at monthly grain instead. For fiscal calendars and named activities, [prepare and certify the calendar](/docs/latest/modeling/dates/#business-calendars) before selecting its grain. Source parsing and report timezone are separate choices; use explicit parser timezone only for naive timestamps, not aware timestamps or date-only encodings.

Raw local timestamps use the declared source timezone or its resolved reader default for constant-bound membership. Repeated clocks select the later occurrence; skipped clocks select the transition instant. Filtering and calendar buckets share this wall order, so the first repeated hour can be empty. Projected values retain backend-native conversion. Expressions without raw lineage retain native filtering. Use aware timestamps when the exact occurrence matters. Session boundaries and sample completeness retain their own validation.

`ms.hour_prefix(date_field)` inherits the prefix's source timezone context and reader default when combining a civil date with an hour. It has no separate timezone parameter; changing the report timezone does not reinterpret the source.

## Time means and sample coverage

`sample_interval=(1, "hour")` declares expected clock points; it does not round event timestamps to hours. Time-sample `mean` and `weighted_mean` aggregate represented samples without filling missing clocks. Explicit Population sample domains and existing NULL/weight policies remain unchanged.

Continue with the six-order model: first average order amounts per order date, then average the represented dates within each region. This model declares no regular sample interval. Only dates with orders participate. August gives 100 for east and 600 for west; adding zero gives the same results.

```python
order_date_entry = session.catalog.get("time_dimension:sales.orders.order_date")
assert order_date_entry.kind == "time_dimension"
order_date = order_date_entry.value
samples = amount.mean(time=order_date).per(order_date)
sample_mean = session.observe({"average": samples.mean()}, by=(august, region)).compute()
# Arithmetic does not add a clock-coverage requirement.
adjusted = session.observe({"average": samples.mean() + 0}, by=(august, region)).compute()
sample_mean.show()
adjusted.show()
```

A strict sample reducer such as `samples.quantile(0.95)` still requires declared clock coverage. Its error identifies the Metric, time field, actual interval and up to six groups with three missing instants each. Existing NULL samples are not missing clocks. Dates have equal weight; if order counts differ by date, this result can differ from an order-weighted mean. Time samples do not automatically form hourly buckets.
