Comparison measures the difference between current and baseline Frames. Attribution breaks a supported target into contributions across a new classification. The [Analysis DSL guide](/docs/latest/analysis/dsl/) has the shared setup and full executable examples for both.

## Choose and align a baseline

Compare Frames from the same Session that represent the question you intend to compare. Completed Frames hold fixed values; `compare` does not rebuild them from their source declarations. If you need a new source read, explicitly create new observations and compare their results. Prepare matching value paths with compatible units before calling `compare`; equal names pair outputs but do not establish that two Metrics have the same business meaning.

Use `on` to declare how complete axes correspond when their names differ or the default pairing is not the intended one. Use `match` to state how calendar or interval coordinates correspond when their keys differ. These choices express business correspondence; compatible key shapes alone do not prove it. Named baselines put both rules inside `mv.baseline(...)`.

`compare` keeps current values and adds baseline, absolute-change, relative-change, and row-presence columns. Relative change is `(current - baseline) / abs(baseline)`. A zero baseline gives NA; missing rows and NA values remain missing. Presence indicates that a row exists, not that its value is non-NA. Comparison uses an outer coordinate match, but every baseline time row must map into the current declared time domain. Use [`align`](/docs/latest/analysis/dsl/#compare-and-align) when you need a general union of time domains.

See [compare baselines in the Analysis DSL](/docs/latest/analysis/dsl/#compare-and-align) for the `compare` parameters and a complete example.

## Attribute a supported change

Use `attribute(by=...)` when you need contributions for a selected direct Metric or supported comparison output, broken down by a new semantic classification. The report includes contributions, contribution shares, a freshly read `total`, the input Frame's `observed_total`, and method facts that describe the calculation. Read both totals when a source may have changed since the original observation: attribution fixes the completed parent keys and values. Exact rules read parent and fine inputs separately; Shapley caches endpoints from captured states or native coalition queries. Independent reads have no shared-snapshot guarantee.

Exact additive/rate-mix rules remain exact. Qualified paired nonlinear and quantile targets use whole-Metric group-replacement Shapley with `permutations=1024, seed=0` by default. State routes capture inputs once and sample locally; Float SUM/AVG use summary reconstruction with disclosed bias without an error bound that permutation SE does not measure. Other admitted targets query the original backend for each uncached coalition; query cost can grow with permutations. No consistent snapshot or temporary materialization is required. `contribution_std_error.<name>` describes permutation variation for states and observed marginal variation for independent queries, which cannot isolate source changes. State routes prove all coalition domains; query routes validate visited coalitions. Read the [DSL's route and backend limits](/docs/latest/analysis/dsl/#attribute--explain-source-contributions).

This example uses `session`, `revenue`, `july`, `august`, and `region` from the [DSL setup](/docs/latest/analysis/dsl/). It attributes the absolute change in the shared sample by region:

```python
overall_current = session.observe({"revenue": revenue}, by=(august,))
overall_baseline = session.observe({"revenue": revenue}, by=(july,))
overall_change = overall_current.compare(
    {"reference": mv.baseline(overall_baseline, match=mv.ordinal())}
).compute()
target = overall_change.select({"revenue": overall_change["reference.absolute.revenue"]})
explained = target.attribute(by=(region,)).compute()
assert explained.to_pandas()["contribution.revenue"].tolist() == [-100, -100]
```

In this sample the parent change is -200, with -100 attributed to each region. These are method-based arithmetic contributions under the declared Metric and scope; they do not establish that either region caused the change. A grouped comparison can show how values differ by region, but use `attribute` when you need contributions to a selected target.

If a parent selection must stay fixed for follow-up analysis, complete it first. `attribute` retains those selected keys and does not rerank them after its fresh reads. For a separate source question, `session.population_from(frame, on=...)` can carry selected complete ordinary keys into a new observation. Use the Population in `by` to define the output domain, and `where=mv.in_population(...)` to restrict source contributions. The source declaration is process-local: independent reopen retains fixed results and method facts, but not the declaration needed for another `attribute` request.

For full rules and more examples, see [investigate changes in the Analysis DSL](/docs/latest/analysis/dsl/#investigate-changes) and the [analysis results guide](/docs/latest/analysis/results/).
