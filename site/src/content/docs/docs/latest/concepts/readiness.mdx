`catalog.readiness` checks selected catalog entries, their physical dependency
closures, and any required certified temporal artifacts. It opens no datasource
connection and reads no business rows. Pass `refs` to scope the check; omitting
`refs` checks all loaded physical objects.

Read `status`, `blockers`, and `warnings` together. `blocked` means at least one
blocker was found. `ready_with_warnings` means no blockers were found, but there
are warnings to review. Follow blocker repairs and rerun; each status describes
only the requested scope.

`analysis_ready_inputs` lists directly requested physical refs whose dependency
closures have no blockers. For a handoff, request physical fields or `Entity`
references directly. Selecting a declared `Measure` or `Metric` checks its
physical dependencies, but does not return the derived expression as a physical
handoff input.

A passing result is a static readiness check, not proof of physical type compatibility, current source data,
correct business meaning, or successful execution of the intended analysis. For
physical contracts, use `catalog.validate(refs)`. For current data expectations, add explicit
`ms.source_check` rules and a bounded `scope`, then run the intended observation.
See [Load and validate](/docs/latest/modeling/semantic-layer/#load-and-validate)
for examples and how the checks differ.
