Start with an approved Metric, a member Entity and a question-scoped Session.
Use [the Python tutorial](/docs/latest/guides/python-quick-start/) for a complete local project.
The examples here instead assume a loaded sales model with customers, orders,
revenue and the declared order-to-buyer relationship.

## Construct, execute, inspect

`members()` retains the Entity’s complete ordered primary key. Observation binds the governed Metric and an explicit window; comparison uses current minus baseline.

{/* example: customer-period-change */}

```python
import marivo
import marivo.analysis as mv
import marivo.semantic as ms

session = mv.session.get_or_create("revenue-review", report_timezone="UTC")
customers = session.members(ms.ref.entity("sales.customer"))
revenue = ms.ref.metric("sales.revenue")
buyer = ms.ref.relationship("sales.order_buyer")
current = customers.observe(
    revenue,
    during=mv.time_scope(start="2026-08-01", end="2026-09-01"),
    via=buyer,
    by=(mv.member(),),
)
baseline = customers.observe(
    revenue,
    during=mv.time_scope(start="2026-07-01", end="2026-08-01"),
    via=buyer,
    by=(mv.member(),),
)
change = current.compare(baseline).execute()
change.show()
```

Construction returns a Logical relation without reading business rows or allocating a Run.
Schema-only preflight may connect to establish key/value types. `execute()` admits
and executes the graph, then publishes its Materialized result. Calling a method
on a Materialized receiver constructs new Logical work over retained inputs.

Executing `session.members(entity).execute()` alone reads and saves the complete
member key set. It may scan the entire Entity source, with no default row
truncation. Primary-key uniqueness and an Entity without historical versions do
not limit member count. The graph shares a 600-second execution budget;
`show(n=...)` limits display only.

Use `marivo.help("analysis.LogicalAnalysisDomain")` for the member type, or
`marivo.help(customers.execute)` for an exact receiver method. Method names such
as `group_by` need their receiver: `marivo.help(current.group_by)`.

If execution raises an analysis error, inspect its optional `run_ref` with
`session.get_run(error.run_ref).show()` when present. Errors before Run admission
have no new Run. Source execution after a failure creates a new Run;
`session.runs(status="failed").show()` reads the retained failure history.
`mv.session.abandon_run(session_id=session.id, run_id=run_id)` reconciles an
incomplete or failed Run and its resources while preserving that history.

## Read rows and legal next steps

`show()` reads saved rows. `contract()` describes mechanically admitted actions without reading business rows; it does not choose the next useful business question.

{/* example: bounded-result-display */}

```python
change.show(n=20)
change.show(n=0)
change.show(max_output_bytes=None)
```

The default output budget is 8 KiB, with no default row cap. Whole rows are
omitted when they cannot fit; tags and reasons distinguish Defined, Null,
Undefined and Unknown. `to_pandas()` returns a complete isolated copy and is a
terminal presentation boundary. Display limits do not change execution limits.

## Aggregate original meaning

For this example, `session`, `mv` and `ms` are already bound as above. The sales model declares an additive revenue Metric and its buyer route.

{/* example: customer-original-rollup */}

```python
customers = session.members(ms.ref.entity("sales.customer"))
revenue = ms.ref.metric("sales.revenue")
buyer = ms.ref.relationship("sales.order_buyer")
august = mv.time_scope(start="2026-08-01", end="2026-09-01")
august_revenue = customers.observe(
    revenue, during=august, via=buyer, by=(mv.member(),)
)
total = customers.observe(revenue, during=august, via=buyer).execute()
total.show()
restored = session.artifact(total.state.artifact_ref)
restored.contract().show()
for action in restored.contract().actions:
    print(action.call, action.help_target)
saved_observation = august_revenue.execute()
recovered_observation = session.artifact(saved_observation.state.artifact_ref)
recovered_observation.summarize(method=mv.count()).execute().show()
order_count = ms.ref.metric("sales.order_count")
per_customer_count = customers.observe(
    order_count, during=august, via=buyer, by=(mv.member(),)
)
total_count = customers.observe(order_count, during=august, via=buyer).execute()
merged_count = per_customer_count.rollup().execute()
merged_count.show()
```

`rollup()` merges sufficient original Metric components and finishes the governed
equation. `summarize()` creates a new statistic over current represented rows.
A mean of displayed averages is not the original weighted mean. Grouped
observation over the same Entity root needs no relationship solely for grouping.

For Count, `rollup()` merges the original occurrence counts. `summarize(mv.count())`
counts represented result rows instead. Native-table Count rollup supports
PostgreSQL, MySQL, Trino and ClickHouse on the registered UTC microsecond Ibis
profile. Missing physical support reports the exact key and bounded registered
alternatives; keep the source unchanged and report that key when none is suitable.
Categorical Count retains flat coordinate state, including on PostgreSQL.
Exact method, type, time and physical profile admission still applies.

Ordinary `observe` directly computes the overall Metric. Member scope limits contributions; `by=(mv.member(),)` preserves each complete member identity, and `by=(dimension,)` computes grouped values directly. With `during=grid`, every time bucket stays while `by` selects spatial grain; endpoint reads and cumulative observations bind the grid through `at=grid.before_end/end`. Retain partitions before original rollup when attribution needs them. Numeric, ratio and statistic results retain `group_by`; member domains and Category, Boolean and Temporal results do not. Nonnumeric scalar results retain overall `summarize(mv.count()/mv.count_defined())`. For prescribed report rows, complete an exported `to_pandas()` result externally; external results cannot re-enter typed analysis.

Omitting `by` and passing `by=()` both compute the overall Metric.
`by=(mv.member(), channel)` computes a value for each customer and channel,
retaining the customer's full ordered primary key for subsequent `members()`.
The marker takes no arguments and gets its identity from `customers`; Entity
Refs are rejected in `observe.by`. Use the marker only in `observe.by`; result
`group_by` keeps its existing axis selectors.

Category `read` and chained `.where()` calls return `LogicalCategoryRelation`;
execution and Artifact recovery return `MaterializedCategoryRelation`.
Filtering a Materialized category builds Logical work over the saved data.
Filtering a category used in `by` must still cover all consumed keys; select
its `.members()` before observation to restrict the member scope.

## Group the same Entity

This sales model uses `sales.order` and its declared categorical `channel` Dimension.

{/* example: same-entity-grouping */}

```python
orders = session.members(ms.ref.entity("sales.order"))
channel = ms.ref.dimension("sales.order.channel")
channel_revenue = orders.observe(
    ms.ref.metric("sales.revenue"),
    during=mv.time_scope(start="2026-08-01", end="2026-09-01"),
    by=(channel,),
).execute()
channel_revenue.show()
```

`read` and ordinary member `observe` infer a unique directed keyed to-one path.
Omitting `via` and passing `None` have the same meaning. If several relationship
roles are legal, select a Relationship Ref or `mv.path(first, *rest)`.
`via=(path_a, path_b)` binds roots by identity in any order; it can specify only roots
that need disambiguation. A read accepts one member-to-owner route.
`mv.path(a, b)` composes two hops; `via=(a, b)` selects two independent root paths.
Required matching trusts the consuming contract. Unknown matching is retained
as an unverified premise without a matching precheck.

Contribution attribution and dimension lookup can use different paths. The model
in this next example declares order lines, a line-to-order-to-buyer path, and a
separate line-to-product path. Product categories attach to full line keys before
revenue aggregation. Bare `by=(product_category,)` gives the same result when its
binding is unique. Classifications must cover the complete consumed contribution keys. This is a
trusted premise; violations are not promised automatic detection.
Versioned fields require their own `read(..., at=...)`; an observation window
does not choose an attribute version.

{/* example: contribution-classification */}

```python
customers = session.members(ms.ref.entity("sales.customer"))
lines = session.members(ms.ref.entity("sales.order_line"))
category = lines.read(
    ms.ref.dimension("sales.product.category"),
    via=ms.ref.relationship("sales.line_product"),
)
category_revenue = customers.observe(
    ms.ref.metric("sales.line_revenue"),
    during=mv.time_scope(start="2026-08-01", end="2026-09-01"),
    by=(category,),
).execute()
category_revenue.show()
```

The same Dimension read through different explicit roles retains different
coordinate bindings. Use the corresponding classification object for subsequent
`group_by`, statistic rollup or retained-axis attribution when a bare Dimension Ref
would be ambiguous. Attribution uses the complete ordered endpoint axes. Fixed continuations
use saved bindings and complete keys without re-inferring paths.
Contribution coordinates use flat state on all six backends, including SQLite,
MySQL and ClickHouse. Coordinates already in the result key reuse original
components; other coordinates retain complete flat partitions. Real all-Null
contributions remain distinct from empty targets. Automatic relationships preserve
the exact backend admission boundary. Materialized comparisons retain the bound
endpoint partitions for source-free attribution; old state requires re-execution.
Frozen definitions use shared contract tables so repeated facts and bindings do
not expand at every graph node. This preserves original attribution scope and
source-free continuations within the existing definition budget. Graph snapshots
from earlier formats require re-execution; existing history and files are preserved.

## Keep source and fixed work explicit

A live definition reads current sources when executed again. Recover an exact
past result with `session.artifact(ref)`. Fixed continuations consume retained
parts without replaying origin. Adding a live Metric, field or Event to a fixed
receiver creates mixed work and rejects before either business input is read.

Continue with [time and cohorts](/docs/latest/guides/time-and-cohorts/),
[comparison and attribution](/docs/latest/guides/comparison-and-attribution/),
[statistics](/docs/latest/guides/statistics/) or [evidence and recovery](/docs/latest/concepts/evidence/).
For an unfamiliar capability, start at `marivo.help("analysis")`; with an object
in hand, follow its contract and exact Help target. Structured errors own repair.

## Session discovery

Session discovery reads only the current Store generation. Before that Store is
created, `mv.session.current()` returns `None` and `mv.session.recent()` returns
an empty page. These reads create no Store state. Earlier generation directories
can remain in the same project while you create new Sessions; their Sessions
are not read or migrated. An invalid or unreadable current Store still raises a
structured error.

{/* example: session-discovery */}

```python
import marivo.analysis as mv

current = mv.session.current()
history = mv.session.recent(limit=5)
session = mv.session.get_or_create("revenue-review", report_timezone="UTC")
```

## Saved semantic scope

`mv.session.get_or_create("sales-review", domains="sales")` captures an exact
semantic domain selection. A nonempty sequence is also accepted. Omission
retains an existing scope; conflicting explicit selections fail. Read it through
`session.domains`. Fixed results use saved state independently of current models.
Session metadata uses Store generation 9; existing generation directories remain
untouched and are not migrated.
