Execution logs record submitted SQL and outcomes; usage telemetry records
selected operation events and durations. Both stay in project-local files. Use
Frames to inspect analytical values.

## Find the right records

| Record | Location | Use |
| --- | --- | --- |
| Execution logs | `.marivo/logs/execution-YYYY-MM-DD.NNN.jsonl` | Submitted SQL, outcomes, and durations |
| Usage telemetry | `.marivo/telemetry/events-YYYY-MM-DD.NNN.jsonl` | Operation, outcome, and duration summaries |

Use the query ID to match a SQL submission with its completion.

New execution-log records use `schema_version: 2` and include a `runtime` object with `marivo_version`, `python_version`, `python_executable`, `package_path` and `process_id`. The logger writes these fields; caller context cannot replace them. This identifies the process environment, not the package contents or a data snapshot. Run `marivo doctor` to inspect the current environment; it cannot reconstruct a historical one. Older records are unchanged, and missing `runtime` means the historical identity is unknown. A file can contain multiple schema versions; interpret each line separately.

New usage telemetry events use schema v3, identified by
`marivo.event.schema_version`. Earlier events are not migrated, so interpret
each event according to its own schema version.

The released 0.5.7–0.5.9 versions support `full`; its introduction is covered
in the [Marivo 0.5.7 release notes](/docs/latest/release-notes/0.5.7/). The
current source version, `0.6.0.dev0`, accepts only `on` and `off`.


## Enable or disable telemetry

| Mode | Behavior |
| --- | --- |
| `on` | Default; records selected operations and failures |
| `off` | Disables usage telemetry; execution logs remain enabled |

Set the project default in `marivo.toml`:

```toml
[telemetry]
enabled = "off"
```

`MARIVO_TELEMETRY` accepts `on` or `off` and overrides the project setting.
Invalid environment values are ignored; invalid `[telemetry].enabled` values
in `marivo.toml` fail configuration validation.

With telemetry on, explicit long operations such as analysis execution,
semantic loading and datasource queries emit start and completion events.
Selected short operations emit a completion event, and some operations record
failures only. Successful nested calls are omitted; an absent event does not
prove that no work ran. Use execution logs to inspect SQL activity.

## Understand retention and sharing

Files roll by UTC day into segments of approximately 128 MiB. Each stream keeps
historical records for up to 14 days and prunes them to a 1 GiB historical
budget. Current-day files are not pruned, so a directory may exceed that size.

Execution logs contain submitted SQL, which can include business conditions
and literals. Usage telemetry excludes SQL text and exception messages, but can
include Session questions and the `reason` passed to
`md.raw_sql`. Check both records for sensitive content before sharing them.


Session `question=` records the investigation at creation; `frame.persist(description=...)`
describes one saved result. Neither is a per-observe audit annotation.
`analysis_purpose` has been removed; usage events are not a complete query audit.
