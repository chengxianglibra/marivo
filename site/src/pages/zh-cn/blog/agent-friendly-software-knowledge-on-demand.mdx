做 Marivo 时，除了设计 API 和实现功能，我一直在尝试解决一个问题：如何让 Agent 高效、顺畅地
使用它进行数据分析？Marivo 从立项之初就把 Agent 设定为目标用户。面对一个没有先验知识的
陌生库，Agent 如何找到用法、正确调用，同时避免让无关信息填满上下文窗口，是设计中需要
持续考虑的问题。

传统软件开发已经积累了许多关于易用性的经验：清晰的 API、结构合理的文档、明确的错误说明。
这些经验仍然重要，但使用者的认知特点和交互方式发生变化，也带来了新的设计取舍。本文从
开发 Marivo 的实践出发，讨论供 Agent 使用的库、API 等开发工具可以怎样组织信息，供有
类似需求的开发者参考。

## 先看 Agent 的工作循环

理解这些设计问题，可以先从工具参与的工作过程开始。Agent 的工作可以概括为一轮轮循环：根据
任务和已有信息判断下一步，调用工具或运行代码，读取反馈，再决定继续、调整还是结束。前一次
操作的输出，会成为下一次行动的依据。工具执行和结果传递由 Agent 运行框架（harness）组织，
库和 API 通过这些环节参与循环。

在这个循环里，查阅用法、检查状态和处理错误，本身也都是推进任务的动作。Agent 不必先掌握一个库
或 API 的全部知识再开始使用，可以在工作过程中逐步补齐当前缺少的信息。比如，已经知道要执行
哪个操作，但还不确定参数，就先查询用法；提交后拿到了任务标识，则根据返回的状态决定是否继续查询。

一次调用除了完成自身功能，返回的信息还会影响 Agent 的下一步判断。缺少关键事实，可能带来
额外查找或无依据的猜测；信息太多，又会占用后续工作所需的上下文。因此，返回什么信息、在
什么时候返回，也是接口设计的一部分。

## 使用陌生库，需要补齐哪些信息

Agent 接到任务后，首先需要判断这个库能否解决问题，随后才能选择操作、准备输入并执行。调用
成功之后，还要理解结果、决定是否继续；调用失败，则要判断原因和修复方式。所需知识因此会
随着任务推进发生变化，完整的函数列表只能回答其中一部分问题。

这些信息在传统项目中通常已经存在，只是分布在不同位置：

| 需要了解的信息 | 传统项目中的常见载体 |
| --- | --- |
| 工具解决什么问题，适用于什么场景 | README、项目主页、概览文档 |
| 核心概念是什么，一项工作怎样完成 | 教程、使用指南、示例工程 |
| 操作接受什么输入，输入从哪里获得，默认行为是什么 | API 参考、类型定义、函数签名、docstring |
| 调用会产生什么效果，返回对象处于什么状态 | 接口说明、对象属性、返回值、日志 |
| 为什么失败，怎样修复 | 异常类型、错误信息、排错文档 |
| 结果是否满足任务要求，什么时候继续或停止 | 领域文档、工作规范和使用者的经验 |

这些信息仍然有价值，但分散的入口会增加查找和拼接成本。面向 Agent 时，还需要考虑如何把
它们连接起来，让当前任务所需的信息能够及时进入上下文。接下来的问题，就是在工作循环的
不同阶段，由哪里提供这些信息。

## 在工作循环的不同阶段提供信息

**发现工具时，提供适用范围和工作入口。** README 和快速入门帮助开发者判断一个库是否
适用、从哪里开始。要让 Agent 也能找到这份指引，入口需要接入它自身的能力发现机制。
以 Skill 为例，Agent 先从名称和适用说明中识别与任务相关的工具，再加载正文。Skill 因而
适合承载必要概念、工作方法和判断边界，并指向后续查询入口：先解决“什么时候使用这个
工具、怎样开始”，之后再查找具体能力。这样既保留了入门所需的指引，也不必提前把全量
参数表和运行时状态放进上下文。

**准备操作时，提供足以支持调用的用法。** 函数签名、类型和 API 参考已经能说明接口接受什么，
开发者还可以结合教程和编辑器提示准备调用。把这些说明组织成可直接查询的 Help，就能让
Agent 在执行过程中随时查阅。除了参数怎样填写，还说明输入从哪里来、省略意味着什么、
操作有什么前置条件和效果，减少跨文档
拼接信息后才能开始调用的情况。

**读取结果时，通过统一的展示接口提供可判断的反馈。** 返回对象和结构化字段支持程序继续
处理结果，开发者则可以借助调试器、交互环境或打印字段来检查它。在代码执行型 Agent 的
工作循环中，拿到对象还只是第一步，相关信息需要输出后才能进入模型可读取的上下文。
`.show()` 这类约定统一的展示入口，便为这一步提供了稳定的方式，让 Agent 能够查看不同
结果，减少临时编写打印代码、猜测对象有哪些字段的工作。

展示内容也需要有稳定的组织方式：对象是什么、当前处于什么状态、有哪些关键结果、展示是否
省略了内容，以及可以从哪里继续查看。不同对象可以呈现不同内容，但标签、次序和后续入口
保持一致，有助于 Agent 理解执行结果并判断是否符合预期。例如，Marivo 的 Frame `.show()`
在待计算时展示结构，完成计算后展示固定数据和相关元数据，并根据状态提供后续操作入口。

相关方法可以承担不同层次的读取：简短的 `repr` 用于识别对象，`.show()` 用于直接打印可读
信息，支持 `.render()` 的结果对象还可以将展示内容作为文本返回。结构化字段则保留给后续
程序处理。展示文本与字段来自同一份结果事实，让 Agent 读到的内容与程序继续使用的数据对应。

**处理失败时，提供与当前调用有关的修复依据。** 异常类型、错误码和调用栈帮助开发者定位
问题，排错文档则补充常见原因和处理办法。如果错误反馈还带有本次调用的实际输入、未满足
的条件，以及操作是否已经产生部分效果，Agent 在下一轮就更容易判断如何继续。修复指引
（Repair）可以结合这些事实给出具体建议，减少仅凭错误类别猜测的情况。能够修正参数时，
错误可以指出具体位置；缺少业务选择时，可以说明需要用户确认什么。例如，无法确定时区时，
错误信息可以指出如何显式指定时区，但业务上应选哪个时区，仍然需要调用方判断。

## 按使用场景组织渐进披露

确定信息在哪个阶段出现之后，还需要决定一次提供多少、怎样连接。文档中的目录、专题指南
和交叉引用，已经为逐步深入提供了基础。把这套组织方式用于工作循环，还要考虑每次查询
返回的内容能否支持下一步行动：拆得过细会增加查询往返，一次塞入全部内容又会带来无关
信息。比较合适的组织单位，是当前任务中一段连贯的工作。

**Help 按“能力概览—使用场景—精确接口”分层组织。** 文档站点通常通过导航目录区分概览、
指南和参考。这种层次也可以进入 Help 的查询接口，让每一层返回当前所需的说明和更具体的
查询入口：概览帮助 Agent 找到方向，场景说明连接常用操作，精确参考提供完整参数和边界。
例如，Marivo 的分析 Help 会引向输入、操作、执行和结果等入口。Agent 可以根据当前缺口
继续深入，已知接口也可以直接访问，不必逐层浏览。

**连贯使用的 API 放在一起，让一次查询支持一段工作。** 按模块和类组织的 API 参考便于精确
查找，教程则展示接口如何配合。将教程中一段完整的操作路径放进对应场景的 Help，相关用法
就能随一次查询进入上下文。例如，Marivo 的分析起步示例把“查找指标、选择范围、
计算、查看结果”放在同一处，展示前一步的返回值如何成为下一步的输入，减少逐个查函数后
再自行拼接调用关系的工作。场景示例提供可参考的路径，不要求每个任务都重复其中的全部操作。

**参数解释贴近调用，必要约束在行动之前可见。** 类型和默认值是参数文档的基础，输入对象
的构造方法、默认值对应的业务含义则可能在其他章节。将影响这次调用的说明放在参数附近，
并给出准备输入的入口，可以减少查阅中的跳转。例如，Marivo 的 `observe()` 在指标参数旁提供
查找和获取入口，也说明省略筛选参数意味着不额外添加筛选。这样，Agent 在查看用法时就能
了解怎样准备输入、缺省行为是否符合任务要求，减少通过失败来摸索规则的需要。

**不同层次的说明共用契约事实，减少版本漂移。** 从代码和 docstring 生成 API 参考，是保持
文档与实现同步的常见做法。Help 和场景入口也可以沿用这一做法，复用当前签名、类型及
默认值，避免渐进披露变成多份独立维护的说明。Marivo 的 Help 从实际方法取得
签名，同时由开发者维护输入含义、约束和效果说明。例如，分页默认读取多少行可以从签名
取得，但分页是否触发计算，仍需要明确解释。自动生成能够减少重复维护，却不能替代这些
行为说明。

**有限展示说明当前范围，并保留继续读取的入口。** 摘要和分页原本就用于控制输出规模，
开发者可以根据文档约定或界面提示继续查看。工具返回的结果也需要说明哪些内容已经展示、
是否还有内容，以及如何继续读取。例如，Marivo 的 `read_page()` 返回总行数、是否还有
更多数据和下一页游标。有了这些信息，Agent 可以根据任务决定是否继续查看，也能区分
“当前没有展示”与“完整结果中不存在”。

## 如何评估和检验效果

这一部分可以准备一组常用任务作为基准测试，让 Agent 实际运行。先记录全部
任务的完成率和结果正确性，再比较成功任务的三个效率指标：首次进入实际处理的轮次、总轮次
和总 token 消耗。失败任务单独保留原因和执行记录，避免把失败排除后得出片面的效率结论。

这里以一次模型决策计为一轮，同一轮发起的多个工具调用不重复计入轮次，工具调用次数可以
另行记录。“首次进入实际处理”指首次成功执行与任务目标直接相关的业务操作，用来观察前期
发现和准备的成本。必要的查阅与检查仍然有价值，不能仅凭轮次多就判断为低效。对比修改前后
的效果时，可以在相同环境和模型配置下重复运行同一组任务，减少单次表现带来的偶然性。

另外一个我经常做的事情，是让 Agent 使用 Marivo 进行数据分析，完成后自己总结使用过程中
遇到的摩擦。这样的反馈可以提供改进线索，再结合实际调用记录，确认它卡在哪里、是否重复
获取信息，以及哪些说明没有被正确理解。把任务测试和反馈纳入研发流程，就可以持续观察
改动对使用体验的影响，而不只依赖开发者对接口是否易用的判断。

## 最后

面向 Agent 的工具，其可用性也体现在能力发现、执行和反馈之间的连接。这些连接是否顺畅，
需要放进实际工作循环中检验。

再往深一层看，软件抽象本身就在分配认知责任：哪些细节可以隐藏，哪些规则可以交给程序，
哪些信息必须保留给使用者判断。封装能够降低操作的复杂度，也可能遮住影响判断的重要事实。
“让知识在需要时出现”，意味着在简化使用的同时，保留理解和核查的路径。使用者不必时时
面对全部细节，但需要时仍然能够知道操作做了什么、结果从哪里来，以及还有什么尚未确定。

大语言模型扩大了软件能够理解和处理的问题范围，也带来了更多无法预先穷举的使用
方式。清楚的契约、可检查的状态和具体的反馈，可以在这种开放性中建立一些可依赖的确定性。程序负责
落实已经明确的规则，Agent 和用户则结合目标与情境作出仍需判断的选择。无论使用者是人
还是 Agent，如何划分这条边界、让探索始终有事实可依，都是软件设计需要持续回答的问题。
