# 当前写作要求

以下要求适用于当前中英文使用文档，并优先于本文较早制定的目录建议：

- 主线面向人直接理解和使用 Marivo，Agent 安装与使用集中在一篇独立文档，并提供一句可交给 Agent 执行的安装指令。
- 合并短页。用章节容纳相关任务，不为每个术语或单次调用建立独立网页。
- 语义层和分析 DSL 的深入介绍用代码展示能力；说明文字用于交代输入、结果和限制。
- 其他示例只保留任务所需参数和步骤，不填写无关的默认项。
- Python 代码使用 Ruff pretty format，88 列，多行调用按格式器规则排版。
- 使用具体、直接的表述，删除宣传性修饰、套话和模仿对话的写法。

# Marivo 使用文档写作规范

本规范指导 `site` 下中英文使用文档的整体重写与后续维护。文档的读者是人：
他们需要认识 Marivo、判断是否适合自己的工作，并学会用它完成分析。
即使读者通过 AI Agent 使用 Marivo，页面也必须围绕人的目标、操作和判断来写。

本阶段只制定写作规范；下文的信息架构是后续重写的组织原则，不表示页面已经实现。

## 1. 文档目标与范围

使用文档必须依次回答三个问题：

1. **Marivo 是什么？** 它解决什么问题，适合谁，在分析过程中承担什么工作。
2. **Marivo 能做什么？** 哪些任务可以完成，需要什么输入，会得到什么结果，有什么限制。
3. **怎么使用？** 如何开始、完成一次真实任务、理解结果，并继续自己的工作。

衡量文档的标准是读者能否理解并完成任务，而不是覆盖了多少 API 名称。
完整重写意味着重新组织叙述、教学顺序和示例，不以保留旧段落或旧章节为目标。
技术事实、有效链接和可复用示例应在核实后保留。

默认重写范围是当前中英文使用指南：

- 英文：`src/content/docs/docs/latest/`。
- 简体中文：`src/content/docs/zh-cn/docs/latest/`。

历史版本、发布说明、博客、首页宣传内容、开发者贡献指南及自动生成的 API 参考
分别维护，不因本轮使用指南重写而自动改写。涉及导航和入口时，在重写计划中列明。

## 2. 读者与阅读路径

| 读者 | 需要解决的问题 | 文档应提供的路径 |
| --- | --- | --- |
| 初次了解产品的人 | 是否适合我的数据分析任务 | 产品介绍、具体能力、使用条件、代表性结果 |
| 借助 Agent 分析的人 | 如何提供问题、确认口径、审阅回答 | 安装与准备、首次 Agent 分析、常见任务 |
| 直接使用 Python 的人 | 如何编写并运行分析 | 安装、完整本地教程、任务指南、API 查询入口 |
| 准备数据与业务定义的人 | 如何让团队复用可信的分析口径 | 数据源接入、语义建模、验证与交付 |

这些是同一产品的使用路径，不要求每位读者先学习全部模块。
业务读者不应为了提出问题而先学 Python；Python 读者也不应被迫先配置 Agent。
新项目与已有语义模型的项目应有明确分流，避免把已有准备工作重复一遍。

每页面向一个主要读者和一个主要问题。跨角色内容通过链接衔接，
不要在同一组步骤里来回切换“告诉 Agent”和“编辑 Python 文件”。

## 3. 产品定位与能力表达

产品介绍面向直接阅读和使用 Marivo 的人。Agent 的安装与操作集中在独立页面。
可以采用以下表达作为起点，并按页面上下文调整：

> Marivo 是一个用于业务数据分析的 Python 库。它把业务指标的定义、
> 分析计算和结果证据连接起来，帮助你和 Agent 使用一致的业务口径开展分析、
> 保存结果并检查结论的依据。你也可以直接通过 Python 使用它。

英文对应表达：

> Marivo is a Python library for business data analysis. It
> connects business definitions, analytical computations, and evidence so you
> and your agent can use consistent definitions, save results, and inspect the
> basis for a conclusion. You can also use it directly from Python.

定位用语必须与当前公开契约一致。不得把它写成自动理解任意业务、自动确定原因、
保证结论正确，或无需准备数据与定义就能回答所有问题的产品。

能力介绍以任务和价值开头，再介绍承担该任务的概念。例如：

| 能力主题 | 首先回答的用户问题 |
| --- | --- |
| 接入与查看数据 | 我的数据在哪里，如何连接，能查看哪些结构与样本？ |
| 复用业务定义 | 如何统一收入、订单、客户等口径，减少重复定义？ |
| 开展分析 | 如何观察指标、比较时期或群体，并使用适合问题的方法？ |
| 保存与继续工作 | 如何保存结果，之后读取并开展后续分析？ |
| 检查分析依据 | 如何查看计算结果、分析范围、证据与方法限制？ |

这张表规定介绍方式，不是完整能力清单。重写前应根据当前实现核实具体方法、
数据源与使用条件；设计提案中的能力不能直接进入使用指南。
“支持比较”之类的描述应配一个实际问题、所需输入和结果说明。
只有真实验证过的条件才可以写成兼容性、性能或可复现性承诺。

## 4. 信息架构与渐进教学

整体顺序遵循“认识产品 → 完成一次任务 → 扩展使用 → 按需查询”。
以下栏目表达内容职责，实际页面名称和路由在重写计划中确定。

| 内容层级 | 主要内容 | 不应承担的内容 |
| --- | --- | --- |
| 认识 Marivo | 定位、适用场景、能力、输入与结果、路径选择 | 完整术语表、内部架构与 API 清单 |
| 开始使用 | 安装、必要准备、首次 Agent 分析或 Python 分析 | 一次讲完所有概念与边界 |
| 按任务使用 | 接入数据、定义指标、比较、时间分析、保存与读取等 | 按源码模块逐个介绍函数 |
| 理解关键概念 | 解释影响使用选择的业务定义、分析范围、时间、结果与证据 | 编译器、存储格式等实现细节 |
| 查询与排错 | 环境、配置、支持范围、常见错误、API 入口 | 重复完整教程 |

入门页只提前解释完成当前任务必须知道的概念，其他概念在首次需要时引入。
概念页应从一个具体困惑开始，给出例子，再解释规则和对使用的影响。
任务页应从“我要完成什么”组织，而不是从类、方法或参数的排列顺序组织。
精确签名交给 API 参考和 Live Help；任务所需的用法仍须在正文讲清，
不能用“去查 Help”代替教学。

每个重要事实应有一个主要说明页面。其他页面给出足够理解当前任务的摘要并链接过去，
避免多份完整安装流程、同义的快速开始和互相循环的前置阅读。

## 5. 页面写作模板

模板用于检查完整性，不要求每页机械地使用相同标题。

### 产品与能力页

先说明读者能解决什么问题，然后给出一个具体场景和结果，解释 Marivo 承担的工作、
必要准备和主要边界，最后提供明确的使用入口。标题与摘要应直接表达用途。

### 教程与任务指南

1. **目标与结果**：读完后能完成什么，最后会看到什么。
2. **必要准备**：需要的数据、项目、版本、权限或前置教程；只列当前任务所需条件。
3. **操作步骤**：每步说明做什么、为什么做，以及必要的检查点。
4. **理解结果**：解释关键数值、字段、范围和下一步判断。
5. **处理常见问题**：只处理本任务最可能遇到的障碍，其他情况链接排错页。
6. **继续使用**：推荐与当前成果直接相关的下一步，通常一至三个链接即可。

独立教程必须能从声明的起点走到结果。承接教程必须链接到明确的准备步骤，
说明复用哪些文件或变量，不允许依赖读者猜测的会话状态。

### 概念与参考页

概念页回答“它是什么、什么时候需要、会改变什么选择”，配合具体例子。
参考页回答精确的查询问题，使用表格或短条目组织条件、选项和限制。
排错条目按“现象 → 可能原因 → 如何确认 → 如何修复”组织。

## 6. 面向人的语言

- 先讲业务动作与效果，再引入技术名称。首次出现时解释术语，不靠大写或英文暗示含义。
- 使用自然、具体的句子，一段围绕一个问题。避免连续堆叠名词和没有主语的命令。
- 明确动作的执行者：用户确认业务口径，Agent 组织分析，Marivo 执行受约束的计算。
- 不把 Agent 的内部工作顺序、工具调用约定或提示词规则直接复制为用户教程。
- 避免无依据的“强大”“智能”“无缝”“一键”“任意”等宣传词。
- 限制放在影响用户选择或解释结果的位置，说明实际后果；不要每页重复全部技术边界。
- 使用短段落、动作标题和必要的列表。表格用于比较，提示框用于容易遗漏的重要条件。
- 内部术语只在理解行为确有必要时出现，并立即解释；不要将内部实现当作产品卖点。

例如，不宜用下面的句子开启入门说明：

> 构造明确来源分析，compute 固定数据，persist 发布已完成结果，Artifact 拥有审计。

可改为：

> 先计算你选定范围内的指标，并检查结果。需要以后继续使用时，将结果保存下来；
> 保存的结果还附带可供检查的分析记录。

在 Python 教程真正执行这些动作时，再介绍对应的方法、返回值和行为区别。
易读不等于省略语义：计算与保存、重新查询与读取已有结果等差异仍须在相应步骤讲清。

## 7. Agent 使用说明

Agent 路径必须帮助人完成三件事：准备必要信息、表达问题、审阅回答。

- 明确开始条件：Agent 如何获得 Marivo、使用哪个项目、已有定义在哪里。
  不假定安装 Python 包就自动完成所有 Agent 配置，也不宣称所有 Agent 均兼容。
- 提问示例应包含业务目标、指标、时间或群体范围、比较基准，以及期望的回答形式。
- 解释哪些选择需要人确认，例如收入是否扣除退款、使用哪个业务日历。
- 展示一个有代表性的回答结构，让读者知道如何检查结论、关键数值和局限。
- 明确缺失定义或数据时如何继续，不把未经确认的默认口径藏在示例里。

不要要求业务读者记住内部算子、对象字段和固定调用顺序。
介绍 packaged skills 时说明它们帮助完成什么任务；具体工作规则仍由技能本身维护。
示例对话若为编辑构造，必须标注为示意，不得伪装成实际执行记录。

## 8. 代码、数据与结果示例

核心教程优先使用一个小型、确定性的本地业务数据集，例如订单收入。
统一指标名称、日期、金额单位与数据口径，让读者把注意力放在新能力上。
专题确实需要另一类数据时，应明确交代切换原因及数据含义。

每个可执行示例必须满足：

- 标明安装版本或开发环境要求、额外依赖、运行目录、文件名和执行命令。
- 提供必要数据或可靠的获取方式；不能把私有数据库、未提供的项目文件或凭据当作默认条件。
- 交代观察粒度、纳入范围、单位和相关时间边界；涉及缺失值、重复、分母或连接时解释其影响。
- 使用当前公开入口和经过验证的名称；代码、变量、注释和数据标识符保持英文。
- 可复制代码不含省略号、虚构 API 或未定义变量。摘录须标明依赖的完整示例。
- 展示关键预期结果并解释含义，不能只展示代码。数值结论必须能由示例数据独立核对。
- 对需要替换的值明确标记；凭据通过环境变量等受支持方式提供，不写入示例文件。
- 需要复用计算结果时使用对应返回值，并解释保存、重开与重新读取来源之间的差别。

模拟结果、输出节选和真实运行结果须区分；动态 ID 与时间可省略或标注为示意。
不要依赖终端输出的每个空格来教学，也不要把整段调试日志作为预期结果。
重跑会覆盖文件、修改数据库或产生外部费用时，在相关操作前说明具体影响。

图表应解释真实数据或帮助理解流程，并提供必要的文字说明、单位与替代文本。
不用装饰性架构图替代操作步骤；截图也不能替代可复制命令和结果解释。

## 9. 中英文一致性

中英文是同一套使用文档的两个完整版本，应在同一次内容变更中同步。
可以先用更适合作者的语言起草，但第二语言必须独立通读，不能停留在逐句机器翻译。

- 页面目的、前置条件、步骤、能力边界和结论一致；语言组织允许符合各自阅读习惯。
- 代码、命令、数据、数值和 API 标识符保持一致，避免两种语言演示不同的产品行为。
- 标题、摘要、导航和图片替代文本都要本地化；中文正文避免无意义的中英混排。
- 同语种页面优先互链。只有目标没有本地化版本时才跨语言，并说明目标语言。
- API 标识符保持原样并使用代码格式；普通说明使用自然的本地语言。

关键术语采用以下规则，并在重写中按实际需要扩充：

| 英文 | 中文正文 | 使用说明 |
| --- | --- | --- |
| AI agent | AI Agent，后文可简称 Agent | 首次解释其在使用过程中的职责 |
| data source | 数据源 | 与具体连接配置按上下文区分 |
| semantic layer | 语义层 | 首次解释为可复用的业务定义 |
| metric / dimension | 指标 / 维度 | 对应具体类型时保留 `Metric` 等标识符 |
| session | 分析会话 | 说明一次分析的上下文；API 类型使用 `Session` |
| AnalysisFrame | 分析结果（`AnalysisFrame`） | 技术页说明待计算表达式与已完成数据等实际状态 |
| Population | 分析对象集合（`Population`） | 说明成员与坐标范围，不简单等同于某张数据表 |
| Artifact | 保存结果的分析记录（`Artifact`） | 按当前契约说明审计用途，与 Frame 数据区分 |
| evidence | 证据 / 分析依据 | 解释支持什么主张及其限制，不暗示已证明业务因果 |
| readiness | 分析准备检查 | 解释检查范围，不将检查通过等同于业务口径正确 |

不得为了术语对齐牺牲语义。例如，不能把待计算的 Frame 直接描述成已经存在的数据。
中文使用中文标点，中英文与数字之间保持必要空格；英文优先使用直接、主动的句式。

## 10. 技术事实与内容分工

写作前按主题核对当前契约、公开 Help、实现和可运行示例。
现有使用文档是待核实材料，不能因其已经发布就直接照抄。
若契约与实现冲突，先查清预期行为并记录差异，不通过润色文字掩盖问题。

| 材料 | 主要职责 |
| --- | --- |
| site 使用文档 | 产品理解、任务教学、结果解释、实际选择 |
| Live Help 与 API 参考 | 精确 API、参数、类型、约束和查询入口 |
| 架构与设计文档 | 拥有契约、技术原理、设计决策与提案状态 |
| packaged skills | Agent 工作方法与判断边界 |
| 发布说明 | 特定版本的变化与迁移信息 |

每篇页面在重写工作记录中保留核对来源和示例验证结果，避免把源码路径、评审轮次、
测试数量或内部验收术语放进用户正文。正文只保留影响用户使用的版本、条件与限制。

`latest` 当前跟随开发实现，不能把开发 API 配上仅安装旧发布包的命令却不作说明。
已发布包可用、开发环境可用、本地示例通过、特定外部数据源通过是不同事实。
安装说明与教程必须指向同一个可用环境；尚未实现的能力应留在设计材料中。

优先查阅以下仓库内来源，再沿相关主题深入：

- [语义与数据源概览](../docs/architecture/semantic/overview.md)。
- [分析架构与当前契约](../docs/architecture/analysis/README.md)。
- 当前环境中的 `marivo.help("authoring")`、`marivo.help("analysis")` 及对应聚焦目标。
- [site 维护说明](README.md)。

## 11. 重写与维护流程

先确定读者路径与页面职责，再写正文。后续重写按以下步骤推进：

1. 盘点当前页面，标明重写、合并、删除或保留及理由，建立中英文对应关系。
2. 为目标页面写一句读者问题，列明前置条件、关键成果、事实来源和示例依赖。
3. 先完成产品介绍与一条端到端教程，检验语言和教学方式，再扩展任务专题。
4. 核对技术事实、运行必要示例、解释结果，然后完成另一语言并交叉检查。
5. 检查导航、链接、页面渲染与完整阅读路径，依据下节标准验收。

工作记录应能看出页面负责人、依赖、当前状态、待解决问题和验收证据。
沿用现有文档与检查机制，不为本次重写另建通用文档管理框架。

文件和路由维护遵循当前站点机制：

- 页面标题、摘要与正文一致；新增或调整页面时同步 `docs-versions.mjs`、导航和相关检查。
- 改名或合并页面前检查现有入口，明确旧链接的去向并验证跳转；不能静默制造断链。
- 共享历史页面受 `shared-docs.json` 和基线约束，先按 [维护说明](README.md) 确定影响范围。
  不直接编辑生成副本，也不为让检查通过而盲目重写历史内容或更新哈希。
- API 参考由生成流程维护，不直接编辑 `public/api/` 中的生成结果。
- 本规范不扩大对 `AGENTS.md` 或 packaged skills 的编辑权限。

## 12. 验收标准

重写后的文档必须通过以下检查：

- **产品理解**：新读者读完入口页，能说清 Marivo 的用途、主要能力、必要准备和自己的入口。
- **路径完整**：Agent 与 Python 路径分别可从声明的起点走到可检查的结果，无隐藏前提或循环阅读。
- **任务可完成**：教程说明做什么、如何做、看到什么，以及如何判断结果符合预期。
- **语义准确**：指标、范围、时间、单位、缺失值及方法限制在需要时讲清；不把关联或贡献分解写成因果证明。
- **事实可靠**：关键能力可追溯到当前契约与实现；执行示例有记录，预期数值有独立核对依据。
- **语言自然**：入门页不靠内部术语串联；技术细节服务于使用决策；没有照搬 Agent 指令的段落。
- **双语等价**：两种语言都完整可读，步骤、代码、结果、限制和链接对应。
- **站点可用**：标题层级、代码块、表格、提示框和移动端阅读正常；导航、路由与锚点可达。
- **维护清晰**：事实有主要说明位置，示例依赖明确，历史版本未被意外改写。

验证按实际改动执行：仅修改本规范时检查内容、文件链接和 diff；
重写使用页面时在 `site` 运行 `npm run verify:content` 与 `npm run build`，
并实际验证受影响的可执行教程和代表性页面渲染。共享页面机制有改动时增加
`npm run test:shared-docs`。站点构建成功不等于示例正确，也不等于人能读懂。

最终审阅应模拟一个首次使用者，沿主要路径从头走一遍。发现不懂的术语、缺失的准备步骤、
无法解释的结果或无效的下一步时，应修正文档，而不是要求读者自行补齐作者的隐含知识。
