# Marivo 测试质量规范

本规范定义测试目标、准入标准、评审准则以及删除合并规则，适用于单元测试及其与组件、Runtime、发布验收的分工。测试必须服务于当前功能契约，以合理的运行和维护成本发现真实缺陷。

本规范是测试工作的要求，不是现有测试已经全部符合要求的声明，也不改变 pytest markers、Make 入口或 CI 配置。普通改动按涉及范围执行，无需为每个用例建立独立台账。

规格、实现和测试发生冲突时，先确认当前 owning contract。提案、旧快照或现有实现的输出均不能单独决定预期值；未经确认不得通过放宽断言、修改快照或恢复退役 API 消除失败。

## 2. 测试目标与优先级

测试应当发现契约破坏、定位原因，并允许保持行为的实现重构。优先覆盖影响严重、难以察觉、容易复发或位于公共边界的错误。数量、行覆盖率和全绿结果不能单独证明功能质量。

| Marivo 风险 | 应保护的事实 | 有效反例方向 |
| --- | --- | --- |
| 数值、聚合与单位 | 值、分母、权重、精度、溢出和单位符合契约 | 不等组大小、零分母、大整数、Decimal、小数与 NULL 混合 |
| 身份、粒度与数据域 | 完整联合键、成员范围、grain、关系 fanout 正确 | 单列键相同但联合键不同；重复关联导致重复计数 |
| 时间与日历 | 时区、半开区间、时间角色、冻结日历与真实边界正确 | 起点、终点、跨月、DST 重复小时；只选相关场景 |
| 空值、缺失与顺序 | 区分无行、NULL、缺失坐标、未定义结果；保留承诺的顺序 | 空输入、全 NULL、present-NA 与 absent、排序并列 |
| 生命周期与所有权 | capture/finalize/resolve 边界、冻结依赖、跨 Session 拒绝、Frame 不可变 | finalize 后捕获；同形但不同所有者；修改导出副本 |
| 持久化与恢复 | 应保留的数值、schema、键、顺序和审计事实；原子发布与故障隔离 | 发布失败仍可读旧结果；缺失 payload；独立进程恢复 |
| Agent 公开契约 | exports、Help 路由、示例、结果与结构化错误指导一致 | Help 指向不存在入口；错误建议不可执行；属性 Help 执行 getter |
| Provider 边界 | 实际引擎的类型、SQL、时间、精度、请求容量和资源处理 | native 行为与本地实现不同；失败后连接未释放 |

这是风险选择目录，不是每个功能必须执行的矩阵。简单类型规则不需要完整旅程；冷恢复不能由同进程缓存读取代替。未承诺的性能、兼容性或执行策略，不应被测试固化成新契约。

## 3. 测试粒度与执行门禁

单元以一个可解释的行为为单位，可以包含多个紧密协作的真实对象；不要求每个函数或类分别建立测试，也不要求全部依赖 mock。

| 范围 | 主要责任 | 不能单独证明 |
| --- | --- | --- |
| 单元 | 数值内核、表达式约束、类型规则、局部状态转换 | 公开入口已经正确连接该规则 |
| 本地组件／集成 | 声明、解析、执行、Frame 与存储的真实连接 | 外部 provider 的具体行为 |
| Runtime | 已启动服务上的真实 provider 风险 | 未运行的 backend/method/type 组合 |
| 安装／旅程验收 | 安装来源、打包资源、独立进程与代表性用户流程 | 全部局部边界和所有数值均正确 |

选择能真实暴露该错误的最小、成本合理的边界。局部规则在主要位置覆盖边界，上层保留必要的连接验证。若故障只在集成时出现，保留真实集成回归，无需强行制造 mock 单元测试。

测试范围与执行成本是两个维度。`make test` 是默认本地回归集，包含单元和本地集成测试；`slow` 标记扩展本地用例，未同时标记 `release` 或 `runtime` 时纳入默认集；`runtime` 是外部服务依赖，`release` 是发布边界，均不是测试质量等级。具体选择遵循当前配置，不为改善统计而更改 marker。

## 4. 新增与修改测试的准入标准

每个新增或实质修改的测试，应从名称、数据、断言及必要的简短说明中回答：

1. **契约**：保护哪项当前行为或内部不变量？
2. **失败模式**：至少一个什么样的错误实现会被它识别？
3. **判断依据**：为什么预期结果正确，是否独立于被测逻辑？
4. **边界**：为什么这个层次与 fixture 足以验证该行为？
5. **增量价值**：相对现有测试增加了什么独特风险或连接证据？

不能回答时，先修改设计。复杂或昂贵的测试在说明中补充必要依据；不要求为每个普通用例新增文档、编号或证据包。测试名称、代码和注释使用英文，例如 `test_mean_uses_original_sample_weights`。

新增功能或行为变化需要相关行为证据，优先扩展已有测试；修复缺陷需要可辨认该缺陷的回归。保持行为的重构可复用已有有效测试，无需按修改行数新增用例。文档改动按内容、引用及一致性检查，不自动触发运行测试。

## 5. 数据、预期值与断言

### 5.1 独立判断依据

- 使用可手算的小数据、独立参考实现、独立编写的 SQL 或已确认数学性质；不得调用被测生产函数生成预期值。
- 参考路径不能复用正在验证的 lowering、时间转换或聚合逻辑。使用相同数据库并不自动独立，也不自动无效，应检查是否共享疑似错误来源。
- 保存过的结果、重放结果、序列化往返和两条生产路径相等，仅证明各自的一致性。它们可能共同保留错误，数值正确性仍需独立依据。
- 可以复用输入 builders；预期值计算不得藏入复杂 fixture，形成另一份难以审查的生产算法。

例如，验证基于原始样本的总体均值：A 组为 `[100]`，B 组为 `[0, 0, 0]`，结果是 `25`。直接平均组均值会得到 `50`。不等组大小能区分这两种实现；等组大小不能。这是反例设计示例，不赋予固定 Frame 从组均值恢复原始样本的能力。

### 5.2 有效断言

- 一个测试聚焦一个行为，可用多个断言共同证明它。数值检查按契约包含必要的键、单位、NULL/presence、dtype 和顺序；仅检查非空、类型或行数通常不足。
- 整数、Decimal 和身份键按契约精确比较；浮点容差应依据算法、量级和误差传播，不得为消除失败而放宽。只在契约承诺顺序时比较顺序。
- 错误测试检查拥有该错误的类型和相关结构化字段，如 expected、received、repair。仅 `raises(Exception)` 或任意消息匹配不能证明正确拒绝；拒绝时机有契约要求时还应验证副作用。
- 不固定无关内部对象形状、私有调用顺序或偶然的错误校验优先级。内部算法可直接测试，但应保护其输入输出或明确不变量。
- `__all__` 集合快照保留公开边界保护。Help 和结果文案优先检查语义事实、导航可达性、预算与示例可执行性；需要精确格式契约时才固定全文。更新快照必须说明契约变化。

### 5.3 替身与 fixture

优先使用简单真实值和真实领域对象。替身用于控制外部 I/O、时钟、随机性、故障或成本边界；不得替掉测试声称验证的计算或集成连接。

只有交互本身属于契约时才验证交互，例如“无效输入在业务读取前拒绝”“固定数据操作不访问 source”“失败发布保留旧结果”。不因实现目前调用某个 helper 就断言其调用次数。

fixture 仅构造达到断言所需的语义。直接构造内部数据可以测试下游行为，不能声明覆盖了公开构造或发布路径。共享不可变输入，隔离连接、Session、文件、环境和进程全局状态；具体操作由 fixture skill 负责。

### 5.4 参数化与性质测试

按失败模式和语义等价类选择参数，每个组合应有可说明的作用。普通业务矩阵由代表性本地路径承担，native 差异由对应 provider 测试承担；不要机械组合所有类型、存储、后端、窗口和恢复模式。已知交互风险保留组合测试。

性质测试适用于集合、键编码、单位代数等规则，必须声明前提和有效输入域，并保留已知反例。不要对浮点加法无条件要求结合律，也不要仅以编解码往返代替已知编码值检查。性质测试和小范围变异测试可按风险选用，不是新增的全仓门禁或依赖要求。

## 6. 评审准则

评审首先核对契约、独立预期值和反例，然后检查边界、隔离和维护成本。使用以下问题决定是否接受：

| 评审问题 | 需要修改的典型情况 |
| --- | --- |
| 错误实现会失败吗？ | 删掉过滤、改错分母或丢失联合键，断言仍通过 |
| 等价重构应继续通过吗？ | 仅私有调用次序或对象布局变化就要求重写大量测试 |
| 是否到达声称的行为？ | fixture 早期失败却被宽泛异常捕获；真实逻辑被 mock |
| 预期值有独立依据吗？ | 复制实际输出；参考值复用同一生产算法 |
| 边界和隔离可信吗？ | 冷恢复复用当前进程；依赖执行顺序、真实时间或共享可变状态 |
| 新组合值得维护吗？ | 只换普通输入值，没有新增失败模式 |
| 变更后证据仍完整吗？ | 删除、合并或改 marker 后独特断言失去覆盖 |

对复杂新增测试，可在变更说明中使用简短的 `Contract / Failure mode / Oracle / Boundary / Validation` 说明；普通测试不强制使用模板。评审不以新增数量或断言数量作为通过条件。

缺陷回归在可行时应证明“修复前失败、修复后通过”。如无法安全重放旧版本，说明限制并检查具体错误变体能否被识别，不得虚构 red/green 证据。无需对每个测试机械执行变异测试。

## 7. 删除、合并与迁移规则

### 可删除的依据

- owning contract 已明确退役，不再承诺该行为；仍适用的数值或边界断言必须迁到当前入口。
- 同一失败模式已有同等可信的覆盖，且没有独特的输入规模、native、进程、故障或公开连接证据。
- 测试仅复制实现、验证无承诺的细节或永远为真的条件；先判断是否应改写为有意义的行为测试。

仅因慢、经常失败、维护麻烦、存在更大的端到端测试或降低通过率，不足以删除。不能用 skip、xfail、放宽断言或移出默认集隐藏回归。确需暂时隔离不稳定测试时，记录问题、失去的覆盖和恢复条件，遵循项目评审流程，不能声称相关行为已经验收。

### 合并和迁移的操作要求

1. 列出本次移除的独特行为或失败模式，以及保留测试的位置；很小的修改在变更说明中列出即可。
2. 比较判断依据和边界，而非只比较名称、执行到的代码或相同最终数值。高层用例偶然经过同一分支不等于有效覆盖。
3. 优先合并重复 setup 或参数化同一规则；不同故障原因保持可定位，不将独立昂贵场景塞入一个大循环。
4. 保留必要的空值、联合键、原子发布、损坏输入、source-offline、native 与独立进程证据；不同风险不必保留在同一个测试中。
5. 后续实际修改测试时，检查收集结果和 marker 路由，运行相关剩余测试及要求的门禁；同时清理无消费者的 helpers、fixtures、模板和陈旧说明。

覆盖所有权或执行入口改变时同步覆盖文档。不得改写历史验收记录来声称新的测试布局早已验收。

## 8. 执行证据与持续维护

- 从最窄有效检查开始；共享行为或 fixture 变化按仓库规则扩大验证。需要广泛证据时，运行完整 `make check`。相关 slow、Runtime 和 release 边界单独报告。
- 记录实际命令、范围、通过/失败/跳过与阻塞。静态检查、本地数值、真实服务、安装环境和完整用户验收分别表述；未运行或不可用的依赖不是通过。
- 失败先区分功能回归、契约迁移、fixture 问题和环境阻塞。重复运行不能把不稳定性变成正确性证据；排查并恢复确定性。
- 覆盖率用于发现未执行的重要分支，结合断言有效性评估风险，不规定全项目统一的最低百分比，也不以“覆盖率没降”证明删除安全。
- 按需要观察逃逸缺陷、误报、运行顺序依赖、套件与慢用例耗时、维护负担和关键风险遗漏。无需建立测试数量 KPI 或新的统计平台。
- 默认集的反馈时间目标以 `CONTRIBUTING.md` 为准，不是删减必要覆盖的理由，也不是已达成的性能证据。按实测热点选择排查范围；性能优化应比较相同范围，减少覆盖与加快相同测试必须分别报告。
